Boost on a graphics card: Linux and Intel Macs

Research, 2026-10-24. Nothing was run: no model, no inference. I read release pages, npm metadata and file listings, and looked inside the downloaded programs.

Recommendation.
  1. On an Intel Mac, first time one thing that costs nothing: the x64 Mac Boost we already build asks Apple's graphics layer (CoreML) first. Nobody has ever timed it on an Intel Mac. Put a stopwatch on one photo before building anything.
  2. Build route 1 (ONNX Runtime's WebGPU) for Linux x64 and Intel Macs. It is the same model and the same runner we ship, so the pictures stay identical to today's Boost. The program we already use contains it. About 16 to 17 MB to download.
  3. Keep route 2 (ncnn Vulkan) as plan B if WebGPU turns out flaky on real Linux machines. It is smaller on Linux but brings a different model file and an old program.
  4. Never start a GPU job that might silently run on the CPU. Time the first tile, and say so if it is slow.

One test is needed before committing: route 1 on a real Linux PC with a graphics card, and on one Intel Mac. See "What is still unknown".

The two real routes

1. ONNX Runtime WebGPU recommended

The onnxruntime-node 1.23.2 we already pin, asked for the webgpu provider.

Is it there?Yes. The shipped binaries for Linux x64, macOS x64, macOS arm64 and Windows x64 contain the WebGPU provider and its graphics layer (Dawn). Linux arm64 does not: no Linux ARM. The package's own table calls WebGPU "experimental".
Size, Linux x64Library 32.7 MB (about 12.0 MB compressed) + model 4.6 MB. About 17 MB to download, about 38 MB on disk.
Size, Intel MacLibrary 40.0 MB (about 11.2 MB compressed) + model 4.6 MB. About 16 MB to download, about 45 MB on disk.
For comparisonToday's Boost: Windows 23.0 MB, Apple silicon 14.9 MB.
LicenceONNX Runtime MIT; Dawn (the graphics layer inside it) BSD-3-Clause, as ONNX Runtime's own notices list it; the model BSD-3-Clause.
The user needsMac: nothing, it uses Metal. Linux: the Vulkan loader and a Vulkan driver for the card (Mesa for AMD and Intel, NVIDIA's own driver). Most desktop installs have them; minimal ones may not.
Risks
  • Experimental. A driver bug can mean a crash or wrong pixels on someone's machine.
  • Node cannot tell us which device it got. A software Vulkan (Mesa's "llvmpipe") looks like a GPU and is as slow as the CPU. Needs a timed first tile.
  • Linux x64 only: ARM boards, and machines without Vulkan, stay on the CPU.
  • First run compiles shaders: a pause before the bar moves.
WorkSmall. The runner already picks a provider per OS (DirectML, CoreML, CPU); this adds webgpu on Linux, and on Intel Macs if CoreML is slow. Same model, same Lanczos path, same output.

2. Real-ESRGAN ncnn Vulkan plan B

Upstream's realesrgan-ncnn-vulkan program (xinntao) with the model in ncnn form.

Is our model there?Not in the official downloads. They carry animevideov3, x4plus and x4plus-anime only. But realesr-general-x4v3.param (6.4 KB) and .bin (2.4 MB, half precision) exist in several community repos. Where they came from is not stated. The program loads any model name (I read its source), so they would work. We could also convert our own.
SizeOfficial v0.2.0 (April 2022), program alone: macOS 26.8 MB (Intel and Apple silicon in one, about 8.5 MB zipped); Linux x64 11.4 MB (about 3.7 MB zipped); Windows 6.2 MB (not needed, Boost has DirectML). Plus 2.4 MB of model. About 11 MB to download on a Mac, 6 MB on Linux. No Linux ARM build.
LicenceProgram MIT; ncnn BSD-3-Clause; Real-ESRGAN weights BSD-3-Clause. The Mac build has MoltenVK (Apache-2.0) and shader tools built in, so their notices must go in our credits.
The user needsMac: nothing. MoltenVK is inside the program and it uses Metal; the program asks for macOS 11 or later. Linux: libvulkan.so.1 and a Vulkan driver, and glibc 2.29 or newer (Ubuntu 20.04 on).
Risks
  • Upstream is quiet: last release April 2022, last change May 2024.
  • Half-precision model gives slightly different pixels than today's Boost. Needs a side-by-side look.
  • A second program to ship and keep working; unsigned on a Mac.
  • Plus side: it prints the GPU it found, so we can see "llvmpipe" (software) and refuse it.
WorkMedium. A new runner around a command-line program, a new model file to vet, new credits.

Other ideas

CoreML on an Intel MacFree. It is in the same macOS x64 library, and our runner already asks for it first on any Mac. CoreML on Intel uses the processor and the graphics chip (there is no Neural Engine). Never measured: the x64 build "has never been run". Might already be fast enough, or might quietly stay on the CPU.
A faster, honest CPU pathNo driver needed, works on every machine, including Linux ARM and virtual machines. Arithmetic, not measured: the model has about 1.2 million multiply-adds per input pixel, so a 12-megapixel photo is about 15 trillion. At 100 to 200 billion a second (a guess for a laptop CPU) that is 1.2 to 2.5 minutes; a mid-range graphics card at about 1 trillion a second would take about 15 seconds. The tiles are a known total, so the bar can be true. A smaller-photo limit or an 8-bit model could cut it further. This is also the fallback that route 1 and 2 both need.
Not credible CUDA: NVIDIA only, a separate download of hundreds of MB (the package says so itself). OpenVINO, ROCm: not in the prebuilt Node packages. tfjs-node-gpu: CUDA only. A headless browser for WebGPU: far heavier than route 1 for the same result.

What I checked, and how

  • WebGPU in the Node package: the package's own README table (same in 1.23.2 and 1.30.0), and then the actual files in node_modules/onnxruntime-node/bin/napi-v6: searched the binaries for the WebGPU provider and Dawn (found in macOS x64 and arm64, Linux x64, Windows; none in Linux arm64) and for a Vulkan backend (found in the Linux x64 file; macOS has Metal).
  • ncnn: GitHub release lists and zip contents for v0.2.0 (April 2022) and the 2022-04-24 bundle; file type, linked libraries and minimum macOS of the Mac program; the program's main.cpp for how it picks a model.
  • Sizes: raw sizes are file sizes. "Compressed" is gzip -9 on the library: a real tarball will differ a little.
  • Newer ONNX Runtime: npm is at 1.30.0 and its table is the same. We pin 1.23.2. I did not test whether a newer one helps.

What is still unknown

  • Whether route 1 really picks a graphics card on a typical Linux PC, and how fast. Test: one tile through the model with executionProviders: ['webgpu'] on a Linux box with an AMD, Intel or NVIDIA GPU (Harsh's), and on an Intel Mac. Needs a model run, so it waits.
  • Whether CoreML on an Intel Mac is already fast. Test: the existing x64 Boost build, one photo, a stopwatch.
  • Where the community ncnn model files were converted from (only matters if we pick route 2).
  • How common "no Vulkan driver" is among Linux users who would try this. It decides whether the CPU fallback matters more than the GPU route.
