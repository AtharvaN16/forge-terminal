Boost on Linux, on both chips

Research, 2026-10-25. The on-device model was run for real; numbers are measured unless a line says "estimate". No change to the app.

The short answer. Boost can work on Linux arm64 (and on x64 without a working Vulkan driver) without changing the model. The slowness is mostly the program that runs it, not the model.
  1. Now, a few days: on the CPU path use every core (today it uses 2), and give that path an int8 copy of today's model (1.3 MB). A 12 MP photo at 2× goes from 4 min 40 s to 1 min 19 s on one Apple M2 CPU, with the output very close to today's (not identical). This needs no new program, and the Linux arm64 payload is the same kind of file we already build for x64.
  2. If you want zero visible change, or Raspberry Pi class machines to be bearable: run today's model, unchanged, through ncnn on Linux (both chips). Output matches today's (50 dB), and the model part is 4.7× faster than ONNX Runtime at the same cores. The same program uses a real Vulkan graphics card when there is one and the CPU when not, and can tell the two apart by name, so a software "GPU" is no longer a risk. About 4 MB to download. Costs a small C++ program and a cross-build, a few days' work.
  3. Don't: OpenVINO (slower on ARM and 2.5 GB of memory), MNN (slower than ncnn, no Linux arm64 download), swapping to a smaller model (different, softer look), custom ONNX Runtime builds, ffmpeg's neural filters.

Open choice for you: step 1 changes Boost's look a little on flat areas (see the second crop). If that is not acceptable, go straight to step 2.

What is slow today

Boost runs Real-ESRGAN realesr-general-x4v3 (BSD-3-Clause): 32 layers of 64 channels, 1.2 million numbers, 4.9 MB. It works in 256 px tiles with 16 px overlap, always at 4×, and then brings the tile down for 2× and 3× (and 1× for Sharpen, which costs the same as a 4× Boost). Where there is no graphics card, the runner uses ONNX Runtime on the CPU with 2 threads.

On one Apple M2, CPU only (graphics chip and Neural Engine not used), a 256 px tile takes 1.87 s on one core, 0.97 s on the two the runner uses. A 12 MP photo at 2× (4200×2800 → 8400×5600, 247 tiles) took 280 s end to end, 442 MB of memory (measured with the real runner).

Stand-in. No Linux arm64 machine here, so the Mac's CPU stands in for one. An M2 core is roughly 3 to 4 times faster than a Raspberry Pi 5 core (public single-core benchmarks; my estimate, not measured), and about the same as a Linux VM on an M-series Mac, Asahi, or a recent Snapdragon laptop. x64 was not measured: there was no x64 Linux CPU to hand, so the x64 "without Vulkan" row is expected to follow the same pattern but is unproven.

Quality: Kodak photos, 2×

Two tests. Clean: each Kodak photo (768×512, 24 of them) halved with Lanczos, then boosted 2× and compared with the original. JPEG: same, but the half-size copy is saved as JPEG quality 70 first (12 photos), which is closer to a phone photo that went through a chat app. Higher PSNR and SSIM are better; lower LPIPS (a measure of how different two pictures look to a person) is better. Today's model is trained to sharpen and invent detail, so on a clean half-size copy it scores below plain Lanczos on PSNR. That is expected: PSNR rewards staying close to blurry, not looking crisp. What I would do

  1. Week 1. CPU path: use up to 8 cores, add the int8 model (calibrated on photos, pinned by sha), build the Linux arm64 payload, trim the JavaScript resizing and PNG writing, give the working screen an ETA. Raise the "too slow" limit for the CPU path (3 minutes would still refuse a 12 MP photo on a Pi 5). Linux x64 without Vulkan then falls to the same path instead of stopping. Test on one real Raspberry Pi 5 and one x64 laptop without Vulkan, and send me the checklist results.
  2. If the int8 look is not accepted, or Pi-class speed matters: replace Linux's ONNX Runtime payloads with ncnn (CPU + Vulkan), same model, keeping ONNX Runtime for Windows and Mac. This also removes the guess about whether a "GPU" is real: ncnn lists the device by name and the runner can refuse a software one.
  3. Later, optional: offer the compact 4× model as "faster" (about half the cost, a little softer).

How this was measured, and what is not known

  • One Apple M2 (4 performance + 4 efficiency cores), CPU only, nothing else running. Models: Real-ESRGAN realesr-general-x4v3 (BSD-3-Clause); OpenModelDB's NomosUni compact and SPAN 2×, LSDIRCompact v2 (all CC-BY-4.0 by helaman).
  • Images: the Kodak set (free for research); no personal photos. Quality is on halved copies, so it favours models trained on that kind of degradation. A real photo has no original to compare with, hence the first two crops.
  • Not measured: Linux arm64 or x64 hardware, ncnn on x64, int8 on an AVX2-only x64 CPU, a Vulkan GPU on Linux, TFLite. The Raspberry Pi figures are scaled estimates.
  • Scripts and raw numbers: boost-linux-options-2026-10/.
