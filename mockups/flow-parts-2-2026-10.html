05Working ✓ W5

Decided: W5. The bar's hatching drifts and its trail ends in the verb; under the card, one line: the spinner in the mode's colour and what it is doing, in bold. The clock appears only after 3 s. The size search adds one dot per try (at most 8, empty ones faint); a PDF split adds a solid bar, a full cell tall with no knob, and "page n of N". Nothing appears for the first 0.3 s, and there is no minimum time on screen.

You will rarely see this screen. Most conversions finish in a blink: a normal photo to JPEG takes a fifth of a second or less. So the app waits a moment (0.3 s) before showing anything. If the job is done by then, you go straight from naming the file to the result, and this screen never appears. It only shows up for slow jobs: AVIF files, very large photos, compressing to an exact size, and long PDFs. Those can take several seconds, and this is what you see while you wait.
Round one: W1, W2, W3
Only what is true. A single image has no percentage (invariant 7): it reports its phase and the clock is real. The size search reports which try it is on and the most it can take, 8, but it often settles sooner, so that is a limit and never a bar. Split, extract and render report page n of a known total, the one real count. Esc can stop the search between tries; a single encode cannot be stopped, but nothing is written until it finishes.

06Quality ✓ G1

Under that, the measured size in bold and the saving in green (amber if the file would grow). ←→ in steps of 5; the size is measured once you stop, with "measuring…" in between. The slider carries no mode colour; the bar above does.

The question after Format for a lossy target (JPEG, WebP, AVIF), and after "By quality" in compress. DThe drop zone, once a file lands

Today, dropping a file pastes its path into the field and the zone only dims, as it does for any typing. Nothing says the file was recognised until ↵, and by then home is gone. Here the zone answers the drop: the file goes into it and the field is free again.

What changes in the app. A terminal cannot see a drag or turn one away; the first thing the app learns is the pasted paths. So the app reads the files when the paste arrives, not on ↵. ↵ goes on with them, another drop before ↵ adds to them, esc empties the zone. Several images now convert together: batch conversion moves into the app (the engine and the command line already do it), so a drop of photos is never refused. Format, Quality, Name, Working and Done each get a several-file version later.

Round three: the card for one, the list for several

B·2's card when one file is in the zone, D·2's list from two up. Drawn live, then the two states on their own.

A file left out, in red

The app has two colours for trouble: gold warn with ⚠ for "worth a second look" (today's "⚠ 1 skipped"), and red fail with ✕ for errors, drawn as a card with a red frame. A file that could not be read is a failure for that file, so both of these use fail. Both sit under the field, outside the drop zone.

08Done ✓ K3·a

The screen once the file is written. You get here straight from Save as when the job is quick (under 0.3 s, most photos), or from Working when it is not. Today it is a receipt in a green frame: both names, before and after as two bars on one scale, "saved to", then the keys: ↵ another, o open, s show in Finder, and c when compress found a better format.

Three real results, in every concept. A PNG to JPEG that came out smaller; a compress where the app measured that WebP would be smaller still (today's ✧ offer, the c key); and a GIF to PNG that came out larger and lost its animation, with the warning the engine writes. Every number on this screen is measured: the file has been written. Sizes and names here are made up.

Decided: K3·a. Before on top, after under it, each panel as wide as its file is heavy (on one scale, the larger file filling the block). What a smaller file shed is grey hatching after the new panel, its size just past the panel's end; what a larger file added is orange hatching, the new panel as long as the old one. "before" and "after" are tabs on the panels' top edges in each panel's own fill: before dim, after bold white. Between the panels a short arrow in the mode's colour, │ then ▼, points from the old file to the new one. Under it: the change (green smaller, orange larger) at the end of the larger panel, then the folder; the offer and any warning sit low, above the keys. No file card on this screen.

GNeutral grey ✓

Decided: neutral boxes and text greys. Every grey in the app is a pure grey; nothing leans blue. Every frame on this page is now drawn that way. The table gives each swap.

Every grey the app uses leans blue: the panel behind the fields and the drop zone is #252c3a, the dim text #8b93a6. Here each decided screen is drawn three times: as it is; with its boxes in pure grey (the panel, the picker's band, the chips, the slider); and with the text greys neutral too. Each fill keeps its lightness (OKLab L), so only the tint changes; the text greys were then raised for contrast (dim #b0b0b0, quiet #808080), the values the app's theme uses. The colours that mean something (the mode, ✓, the saving, the default's orange) are untouched.
